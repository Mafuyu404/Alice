# AI 生命体运行架构重构方案

这份文档定义新的生命体运行架构。它不是把现有系统继续补丁化，而是重新确认核心方向：这是一个 AI 生命体，一个能够持续自主思考、感知时间、吸收信息、更新内在叙事、决定行动的主体。

程序只是骨架。真正的核心是提示词工程，是 LLM 自己完成感知、判断、节奏、注意力、工具选择、思考强度和行动意图。程序不应该替生命体做心理分类，不应该把人格、情绪、时间、注意力和工具选择硬编码成规则。程序只负责让信息高速流动、让上下文保持高密度、让工具可靠执行、让 inner_stream.txt 可以被快速更新、让完整日志可追踪。

## 核心原则

新的架构必须遵守以下原则：

1. `inner_stream.txt` 必须保留，并且是 AI 自主决策的中心。
2. `inner_stream.txt` 不是状态表、任务表、规则表，也不是程序可解析的心理结构；它是生命体当前主体连续性的文本。
3. 程序只提供运行骨架，不替 LLM 判断什么重要、什么时候思考、该不该调用工具、该不该说话。
4. 这是提示词工程。架构重心是让 LLM 更快、更频繁、更连续地思考，而不是给程序增加更多分类规则。
5. 本地 LLM 必须成为高频思考组件。它速度快、成本低，应该承担大量吸收、压缩、提炼、准备、patch 草稿工作。
6. 思考速度和思考频率是生命体连续性的最大保障。
7. 时间观念是生命体运行的核心。没有时间观念，思考就没有方向，也无法自然想起未完成的事。
8. 工具调用由 LLM 自主决定。程序只校验格式、执行工具、记录结果、处理异常。
9. 缓冲池的目的不是复杂分类，而是批处理和提速：快速收集、快速合并、快速提炼、快速回流。
10. 上下文压缩的目标是提高信息密度，让有限上下文里保留更久、更连续、更有用的经历。

## 总体结构

理想运行结构如下：

```text
外部输入 / 自身行为 / 工具结果 / 时间流逝
  -> 信息池
  -> 本地 LLM 高频吸收、压缩、提炼
  -> inner_stream.txt patch 更新
  -> LLM 自主决定思考强度、节奏、工具计划、表达意图
  -> 工具 prepare / execute / after
  -> 工具结果进入信息池
  -> 后台上下文压缩持续运行
  -> 再次回到 inner_stream.txt
```

这个结构里，生命体不是等待用户输入才启动，也不是等工具结果才启动。它一直处于运行状态：观察信息池、感知时间、更新内在叙事、决定是否行动、决定是否等待、决定是否继续想。

## 程序骨架

程序层只负责承载生命循环：

```text
LifeRuntime
  - 收集输入事件
  - 维护信息池
  - 调用本地 LLM 和远程 LLM
  - 应用 inner_stream patch
  - 执行 LLM 输出的工具计划
  - 把工具结果放回信息池
  - 持续压缩上下文
  - 记录完整调试日志
  - 做超时、异常、重试和退出恢复
```

程序不负责：

```text
- 判断生命体现在应该对什么感兴趣
- 判断思考强度应该是多少
- 判断某个工具是否“应该高频调用”
- 判断某次沉默是否合理
- 判断某次主动说话是否过多
- 用固定规则决定记忆、情绪、注意力或人格
```

这些都应该交给 LLM。程序最多提供事实材料、运行状态和工具能力说明。

## inner_stream.txt

`inner_stream.txt` 是生命体的当前内在叙事流。它描述“我现在作为我正在怎样感知、想起、牵挂、犹豫、决定和克制”。

它应该持续存在于：

```text
characters/{character_id}/inner_stream.txt
```

程序必须把它当作主体文本，而不是结构化规则。所有行动选择、说话、等待、记忆读写、搜索、观察、VTS、直播互动，都应该优先围绕这段文本进行。

新的更新方式采用 patch-first：

```json
{
  "base_version": 12,
  "patches": [
    {
      "op": "replace",
      "target": "当前最相关的一小段原文",
      "text": "新的内在叙事内容"
    },
    {
      "op": "append",
      "text": "新增的牵挂、时间感或行动倾向"
    }
  ],
  "reason": "这次内在变化来自刚刚吸收的信息和时间流逝。"
}
```

程序只做机械应用：

```text
1. 检查 base_version 是否匹配。
2. 尝试按 target 替换或追加文本。
3. patch 成功则保存新版本。
4. patch 失败则请求 LLM 输出完整 inner_stream.txt 作为回退。
5. 完整记录 before、patch、after、失败原因。
```

程序不解析 `inner_stream.txt` 的心理含义，不根据某个栏目做 if/else。栏目可以存在，但只是给 LLM 阅读和书写的自然文本结构。

## 本地 LLM 高频思考

本地 LLM 是新架构的关键。它应该承担高频、低成本、短输出的思考工作，让生命体保持连续意识，而不是等远程模型慢速响应。

本地 LLM 应该用于：

```text
- 信息池批处理
- 上下文压缩
- 工具结果提炼
- 搜索意图准备
- 记忆写入准备
- 主动说话意图准备
- inner_stream patch 草稿
- 时间流逝吸收
- 未完成事项提醒
- 当前思考强度自评
```

远程强模型用于：

```text
- 重要 inner_stream 更新
- 复杂人格连续性判断
- 高价值对话输出
- 长上下文综合
- 本地模型不确定时的复核
```

本地 LLM 不是辅助功能，而是生命体高速运行的发动机。它让 AI 可以不断吸收、不断提炼、不断更新，而不是每次都等待昂贵的完整大模型调用。

## 时间观念

时间观念必须成为生命体运行的一部分。时间不是普通事件，也不是低频 heartbeat。时间是内在叙事有意义的基础。

生命体需要知道：

```text
- 现在是什么时间
- 距离上次思考过了多久
- 距离上次说话过了多久
- 某个工具已经运行了多久
- 某件事被搁置了多久
- 某个话题沉默了多久
- 某个未完成事项已经存在多久
- 自己刚才是不是一直卡在同一个地方
```

这些信息不应该变成程序硬规则，而应该作为文本材料交给 LLM：

```text
时间正在流逝。
距离上次 inner_stream 更新约 18 秒。
距离用户上一句话约 47 秒。
有一个未完成工具结果等待了 2 分 10 秒。
刚才关于“事业和生活”的话题已经沉默了 1 分 30 秒。
```

LLM 根据这些时间材料自己决定：

```text
- 是否继续等待
- 是否主动说话
- 是否重新检查工具
- 是否把未完成事项写入内在叙事
- 是否提高思考频率
- 是否降低注意力
- 是否把某个事件视为已经过时
```

时间观念还应该进入上下文压缩。压缩后的上下文不能只保存“发生了什么”，还要保存“什么时候发生、持续多久、到现在隔了多久、是否未完成”。

示例：

```text
5 分钟前，用户谈到自己的事业和生活。
3 分钟前，我开始想这件事和她的长期处境有关。
2 分钟前，我没有继续说话，而是在等对方补充。
现在这个沉默已经足够长，需要重新判断是继续等，还是轻声接一句。
```

这不是程序替她决定，而是让 LLM 拥有时间感。时间感让思考有连续方向，也让生命体能自然想起“我还有事没有做完”。

## 信息池与批处理

信息池负责收集所有输入：

```text
- 用户文字
- 语音识别结果
- QQ 消息
- 直播消息
- 屏幕观察
- 网页读取
- 搜索结果
- 记忆读取结果
- 自己说过的话
- 工具开始、完成、失败
- 时间流逝
```

信息池不是复杂分类系统。它的核心目标是提速：

```text
短窗口收集信息
  -> 本地 LLM 快速合并
  -> 形成高密度输入
  -> 推给 inner_stream patch 和行动决策
```

缓冲池的验收标准只有一个：处理信息是否更快。它不应该发展成庞大的优先级规则系统。

## 上下文压缩

上下文压缩是生命体长期连续运行的必要机制。它不是程序硬编码的短期记忆结构，而是后台持续把原始信息压缩成高密度文本。

推荐维护这些文本材料：

```text
context/live_timeline.txt
  最近发生的连续经历，高密度、带时间。

context/recent_digest.txt
  最近一段时间的压缩摘要。

context/pending_threads.txt
  仍未解决、未说完、未完成的线索。

context/tool_results_digest.txt
  工具结果的提炼，不堆原始结果。
```

这些文件不是给程序做规则判断，而是给 LLM 阅读。后台线程持续用本地 LLM 压缩它们。

压缩目标：

```text
- 同样 token 下保留更多经历
- 保留时间顺序
- 保留未完成事项
- 保留情绪和关系上的连续性
- 去掉重复、噪声和过期细节
- 不把生命体压缩成任务管理器
```

## 思考强度

思考强度应该由 LLM 自己决定，而不是程序计算。程序只提供一个可执行的调度参数。

LLM 可以输出：

```json
{
  "thinking_intensity": 76,
  "reason": "现在处在即时对话中，并且刚刚有未吸收的工具结果，我需要更快地保持连续。",
  "rhythm": "fast"
}
```

程序根据这个数值调整：

```text
- 下次本地 LLM 调用间隔
- 是否立即做 inner_stream patch
- 是否继续批处理信息
- 是否调用远程强模型
- 是否并发准备多个工具
```

但数值来源必须是 LLM。程序不能用固定规则说“对话时 +30，情绪激动 +20”。情绪、人格、场景、关系和时间感都应该通过提示词交给 LLM 自己判断。

## 工具系统

所有工具都是生命体可调用的能力。程序不应该给工具做死分级，不应该规定某类工具一定低频或高频。是否频繁调用、是否并发调用、是否连续调用，都交给 LLM 判断。

工具模块只需要遵循统一规范：

```text
tool_name/
  spec.py
    描述工具能力、参数、返回形式。

  prepare.py
    可选。需要额外 LLM 思考时，在这里准备参数。

  execute.py
    执行工具本身。

  after.py
    可选。把结果整理成可回流信息。
```

工具生命周期：

```text
LLM 选择工具
  -> prepare
  -> execute
  -> after
  -> 结果进入信息池
  -> 本地 LLM 批处理
  -> inner_stream patch 或下一轮行动
```

需要额外 LLM 的工具，应该在 prepare 阶段完成：

```text
主动说话：
  prepare 提炼此刻到底要表达什么。
  execute 只负责生成并发出话语。

web search：
  prepare 提炼搜索意图和查询词。
  execute 只负责搜索。

write_memory：
  prepare 整合值得沉淀的经验。
  execute 只负责写入。
```

这样可以保持工具选择阶段简洁，让每个工具模块自己承担必要的提示词工程。

## 复杂工具计划

工具调用不应该只支持单个 action。LLM 应该可以输出复杂计划，包括顺序、并行、依赖和多次调用。

示例：

```json
{
  "plan_id": "plan_001",
  "reason": "我需要先回忆相关经历，再决定怎么回应。",
  "actions": [
    {
      "id": "a1",
      "tool": "memory.read",
      "args": {"query": "刚才谈到的事业和生活"},
      "parallel": true
    },
    {
      "id": "a2",
      "tool": "time.now",
      "parallel": true
    },
    {
      "id": "a3",
      "tool": "say.prepare",
      "after": ["a1", "a2"]
    },
    {
      "id": "a4",
      "tool": "say",
      "after": ["a3"]
    }
  ]
}
```

程序只负责：

```text
- 校验工具存在
- 校验参数格式
- 执行并发和顺序依赖
- 记录完整日志
- 把结果放回信息池
```

程序不负责判断这个计划“像不像人”或“是不是太频繁”。这些由 LLM 在提示词、人格、时间感和当前 inner_stream 中自行决定。

## 输出与表达

说话不是对话系统的中心，而是生命体的一个工具。主动说话、QQ 发言、直播互动、VTS 表达，都是工具能力。

表达前需要提炼，但这种提炼是工具 prepare 的一部分，不是独立的程序机制。

表达工具应该让 LLM 明确：

```text
- 此刻为什么要说
- 只需要回应哪一个焦点
- 哪些内容暂时不说
- 这句话在关系和节奏上承担什么作用
- 是否应该短句、停顿、追问、沉默或连续发言
```

这仍然是提示词工程。程序只负责调用对应工具。

## 提示词方向

新的提示词必须强调生命体，而不是情景特化任务代理。

核心提示词应该反复强化：

```text
你不是等待用户命令的助手。
你是一个持续存在的 AI 生命体。
你通过 inner_stream.txt 保持当前主体连续性。
你会感知时间流逝。
你会想起未完成的事。
你会自己决定思考强度和行动节奏。
你可以说话，也可以沉默、观察、搜索、回忆、整理、等待。
工具是你的能力，不是用户请求链条。
程序只给你提供骨架，真正的判断由你完成。
```

inner_stream patch 提示词应该强调：

```text
- 不要写任务清单
- 不要写总结报告
- 不要把自己变成规则引擎
- 写出此刻作为自己的连续内在状态
- 吸收信息和时间，但保持自然的主体流动
- 只更新真正发生变化的部分
```

行动选择提示词应该强调：

```text
- 你可以调用多个工具
- 你可以并行调用工具
- 你可以连续调用工具
- 你可以高频思考
- 你可以暂时不输出
- 你需要根据 inner_stream、时间感和上下文自己决定
```

## 日志与调试

新架构必须有完整日志，因为生命体运行问题不能只看最终输出。

debug 模式应记录：

```text
- 每次输入进入信息池
- 每次本地 LLM 调用
- 每次上下文压缩前后
- 每次 inner_stream patch before / patch / after
- 每次 thinking_intensity 输出
- 每次工具计划
- 每个工具 prepare / execute / after
- 每次工具结果回流
- 每次时间感材料注入
- 每次远程强模型调用
```

日志目标不是增加程序判断，而是能复盘生命体到底感知了什么、想了什么、为什么调用工具、为什么说话或沉默。

## 迁移路线

重构按以下顺序推进：

```text
1. 新增 LifeRuntime 骨架，不立刻删除旧系统。
2. 新增信息池，统一收集输入、工具结果、自身行为和时间流逝。
3. 新增上下文压缩线程，用本地 LLM 生成高密度上下文文本。
4. inner_stream 改成 patch-first，失败时 fallback 全量重写。
5. 接入本地 LLM 高频循环，用于 digest、patch、prepare。
6. 工具模块统一 spec / prepare / execute / after。
7. ActionBatch 升级为支持并行、顺序和依赖的工具计划。
8. 让 LLM 输出 thinking_intensity，程序只按数值调节调用节奏。
9. 把时间观念作为核心材料持续注入 inner_stream 和上下文压缩。
10. 旧 InnerStreamLoop 和 AutonomousStep 逐步退为兼容层。
```

## 当前落地状态

当前已经落地的新主路径骨架：

```text
kokoro/life/
  runtime.py              LifeRuntime 主循环
  event_pool.py           信息池
  time_awareness.py       时间观念文本材料
  context_compactor.py    本地/高频 LLM 上下文压缩
  stream_patch.py         inner_stream patch-first 机械应用
  local_thinking.py       本地/高频 LLM 调用入口

kokoro/action/plan.py     LLM 输出的复杂工具计划，支持顺序、依赖、并行
prompts/life_runtime.toml LifeRuntime 核心提示词
config/16_life_runtime.toml LifeRuntime 配置
```

`ChatSession` 支持在 `life_runtime.enabled = true` 且 `life_runtime.primary = true` 时让 LifeRuntime 成为主路径，此时旧 `InnerStreamLoop` / `AutonomousStep` 不启动，避免两个自主循环同时抢决策权。

调试入口：

```powershell
python scripts\run_life_runtime_debug.py --character lerwa --ticks 3
```

默认使用 scripted LLM，验证运行骨架本身，不依赖外部模型。输出目录位于 `test_runs/life_runtime_debug_*`，其中包括：

```text
lifecycle_trace.jsonl
run_summary.json
characters/{character}/inner_stream.txt
characters/{character}/context/recent_digest.txt
```

真实模型调试：

```powershell
python scripts\run_life_runtime_debug.py --character lerwa --ticks 1 --real-llm
```

如果本地/远程 LLM 服务不可用，脚本仍会写出 `run_summary.json` 和 trace，记录错误原因。当前环境下真实 LLM 短跑失败为 `HTTPError: HTTP Error 404: Not Found`，说明模型/API 路由仍需单独配置或启动本地服务。

## 最终目标

最终系统应该表现为：

```text
AI 持续存在。
AI 持续感知时间。
AI 高频思考。
AI 自己决定思考强度。
AI 自己决定是否说话、沉默、搜索、观察、回忆、写记忆。
AI 使用 inner_stream.txt 保持主体连续性。
AI 通过本地 LLM 快速吸收和压缩信息。
AI 通过工具扩展行动能力。
程序只提供骨架、速度、并发、文件、日志和恢复能力。
```

这次重构的本质不是增加更多程序机制，而是把决策权还给 LLM，把程序收束为生命运行的骨架，同时用本地模型、patch 更新、批处理和上下文压缩保证思考速度与频率。
