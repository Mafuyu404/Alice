# AIRI 记忆系统参考笔记

本文记录对 `D:\work\reference\airi` 中记忆相关设计与实现的阅读结论，用于后续改进 Alice 的角色记忆系统。

## 总结

AIRI 当前仓库里没有完整落地的长期记忆系统。它已经实现的部分主要集中在 Telegram bot 的消息 embedding、相似度召回和上下文窗口扩展；完整的长期记忆更多存在于设计文档、实验平台和 `plast-mem` 边界说明中。

因此，AIRI 对 Alice 的价值不在于可以直接照搬代码，而在于它明确指出了一件事：角色记忆不能只是向量搜索。一个能支撑 AI 生命体连续感的记忆系统，需要把经历、时间、情绪、访问强化、上下文扩展和长期整理放在同一个闭环里。

## AIRI 已经实现的部分

### 消息写入 embedding

`services/telegram-bot/src/models/chat-message.ts` 在保存消息时会为消息生成 embedding，并根据 embedding 维度写入对应的 vector 字段。

这部分是比较常规的 RAG 基础设施，价值在于它把原始聊天消息作为可召回材料，而不是只保留对话历史数组。

### 简单混合召回

Telegram bot 的 `findRelevantMessages()` 使用了语义相似度和时间相关性：

```text
combinedScore = 1.2 * similarity + 0.2 * timeRelevance
```

这说明 AIRI 没有把向量相似度当成唯一依据。即使实现还很简单，它已经承认“越新越容易被想起”是记忆召回的一部分。

### 命中后的上下文窗口

召回命中某条消息后，AIRI 会额外取目标消息前后若干条消息，形成上下文窗口。

这点对 Alice 很重要。角色记忆通常不是孤立事实，而是一段经历。如果只召回一句“雪吱研究过 MC 红石”，角色仍然不知道当时为什么研究、研究到哪一步、情绪是什么、后来有没有继续。

## AIRI 的架构方向

### 记忆分层

AIRI 文档把记忆分为：

- 工作记忆
- 短期记忆
- 长期记忆
- 肌肉记忆

对应到 AI 生命体里，可以理解为：

- 工作记忆：当前上下文、最近发生的事、还在意识表层的信息。
- 短期记忆：最近形成但还不稳定的经历、想法、兴趣和未完成线索。
- 长期记忆：经过多次提炼、强化、稳定下来的认知和经历。
- 肌肉记忆：某些触发和行为之间已经形成近似条件反射的联系。

这不是要程序硬编码人格分类，而是提醒我们：不同记忆材料的生命周期不同，召回方式也不同。

### 记忆条目需要元数据

AIRI 的 `memory_fragments` schema 里包含：

```text
content
memory_type
category
importance
emotional_impact
created_at
last_accessed
access_count
metadata
vector
deleted_at
```

这对 Alice 的启发是：记忆条目不能只有一句自然语言。至少需要保留时间、来源、重要性、情绪影响、访问次数、证据片段等元信息。否则召回只能依赖语义相似，无法形成“经常想起的更容易想起”“强烈经历更容易影响判断”“最近发生的事更贴近当前状态”这些生命感。

### 召回需要重排

AIRI 文档反复强调 reranking，且认为普通 reranker 仍然不够，因为角色记忆还涉及：

- 遗忘曲线
- 记忆强化
- 情绪偏置
- 随机突然想起
- 精确匹配或关键词命中
- 时间相关性

对 Alice 来说，召回不应该是 `top_k vector search`。更合理的是先粗召回，再综合重排：

```text
候选记忆 = 向量召回 + 关键词/精确命中 + 最近时间线 + 当前角色上下文相关项
最终排序 = 语义相关 + 时间相关 + 重要性 + 情绪影响 + 访问强化 + 少量随机浮现
```

这里的排序机制是记忆基础设施，不是替 LLM 做人格判断。它只是把更像“会被想起”的材料送到 LLM 面前，最终如何理解和行动仍然交给 LLM。

### 长期记忆不应直接写语义记忆

`services/computer-use-mcp/coding-plast-mem-bridge-contract.md` 中给出的方向是：

```text
messages -> segmentation -> episodic memory -> semantic consolidation -> retrieval
```

这条链路非常关键。原始对话、工具结果、内在叙事流日志，不应该直接粗暴写成长期语义记忆。更合理的流程是：

```text
原始事件流
  -> 事件切分
  -> 情节记忆
  -> 后台整理、合并、去重、压缩
  -> 语义/认知记忆
  -> 召回
  -> 召回强化
```

这和 Alice 当前“AI 生命体”的方向一致：记忆的核心价值不是存很多句子，而是把经历变成之后会影响她的东西。

### 背景整理线程

AIRI 文档提到类似梦境或潜意识 agent 的后台任务，用于重新处理、索引和更新记忆分数。

对 Alice 来说，这可以对应为本地 LLM 高频后台整理：

- 整理最近生命周期日志。
- 把对话和工具结果压缩成高密度经历。
- 合并重复记忆。
- 提炼认知变化。
- 给旧记忆补充新的关联。
- 为之后的召回准备关键词、标签和证据片段。

这不应该是一个硬编码人格系统，而是记忆维护的后台工程。

## 对 Alice 的改进方向

### 记忆应该成为角色生命活动的核心闭环

理想闭环应该是：

```text
生命活动 / 对话 / 工具结果 / 时间流逝
  -> 事件流
  -> 工作上下文
  -> 情节记忆
  -> 语义与认知整合
  -> 召回
  -> inner_stream
  -> 行动与表达
  -> 新事件流
```

角色的真实感来自这个循环。她不是因为 prompt 里写了性格才像一个角色，而是因为她能记得经历、在合适的时候想起、并让这些经历改变之后的判断。

### 每次生命 tick 应默认带相关记忆

`search_memory` 可以继续作为主动深挖工具，但 LifeRuntime 不应该完全等 LLM 主动调用搜索才有记忆。

每次内在叙事流 tick 至少应该默认注入一小批当前相关记忆：

- 当前话题相关记忆。
- 最近未完成线索。
- 最近几分钟到几十分钟的高密度时间线。
- 当前角色长期认知中最相关的部分。

主动工具调用用于进一步深挖，而不是承担全部记忆入口。

### 记忆召回应扩展上下文

召回结果不应该只是单条文本。每条命中记忆最好带：

- 原始时间。
- 来源事件。
- 前后相邻事件。
- 相关工具结果。
- 当时的 inner_stream 片段。
- 后续是否产生过认知变化。

这样 LLM 看到的是“经历”，不是孤立知识点。

### 写入记忆前需要整合

记忆写入应该通过 prepare 阶段或后台整理阶段完成：

```text
原始材料
  -> 本地 LLM 快速提炼
  -> 判断是否形成事件
  -> 合并重复和相近事件
  -> 形成情节记忆
  -> 必要时提炼为长期认知
```

这符合之前的工具规范：需要额外 LLM 调用的行为，应放在对应工具或对应模块的 prepare/after 中，而不是塞进统一的工具选择阶段。

### 需要 Alice 自己的记忆元数据层

即使底层继续使用 mem0，也应该在 Alice 层维护自己的记忆记录或包装元数据：

```text
character_id
content
source_event_ids
created_at
last_accessed_at
access_count
importance
emotional_impact
tags
keywords
evidence
related_memory_ids
memory_kind
```

注意，这里的 `memory_kind` 是记忆生命周期和召回用途，不是用户域、维度域或外部身份域。当前架构应保持“只有角色维度”，所有记忆属于角色自身。

## 与 Alice 当前方向的关系

这份参考不改变现有总原则：

- Alice 是 AI 生命体，不是助手。
- 程序只是骨架，核心是提示词工程和 LLM 自主决策。
- 记忆系统提供材料和召回能力，不替 LLM 决定人格、情绪和行动。
- 本地 LLM 应大量用于高频吸收、整理、压缩、召回准备和记忆整合。
- `inner_stream.txt` 仍然是主体连续性的核心。

记忆系统真正要解决的是：让角色拥有足够多、足够准、足够有上下文的经历材料，让 LLM 在自主思考时能自然地想起它们。
