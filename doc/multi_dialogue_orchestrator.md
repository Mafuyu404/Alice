# 多角色对话调度器

本文档描述三角色对话的新方案：用户、角色A、角色B 同处一个场景，由第三人称 planner 统一判断话轮，再调用被选中的角色模型生成发言。

旧的 `multi_chat.py` 采用简单轮流发言，容易变成“两个 AI 轮流服务用户”或“两个 AI 自己互聊”。新方案不再以固定顺序决定谁说话，而是让 LLM 从场景整体判断谁该说、是否该沉默、是否稍后再说。

## 推荐架构

采用：

```text
一个第三人称 planner + 两个独立角色 LLM
```

职责划分：

- planner：站在第三人称视角，判断场上下一步发生什么。
- 角色 LLM：只扮演自己的角色，只生成自己此刻会说出口的话。
- 程序：维护共享历史、执行 planner 决策、限制连续发言次数。

不要让两个角色模型各自决定“我要不要说”。那样会产生抢话、冷场、重复回应和程序仲裁复杂化。话轮决策集中在 planner，角色模型只负责把已决定的发言说好。

## 为什么不用单模型同时扮演两个角色

单模型扮演两个角色适合低成本小剧场，但不适合作为本项目长期目标：

- 两个角色容易被同一种文风污染。
- 角色独立性弱，更像作者写剧本。
- 记忆、情绪、认知层很难拆分。
- 后续无法自然支持不同模型、不同语音、不同立绘状态。

两个独立角色模型更符合拟人方向：

- 每个角色有自己的 system prompt、记忆、认知、情绪和说话节奏。
- 文静角色可以真的少说，活泼角色可以真的多接。
- 可以给不同角色配置不同模型、温度、语音和立绘。
- AI 之间的互动更像同一场景中的两个独立角色。

## 场景模型

场上有三类参与者：

```text
用户 / 角色A / 角色B
```

共享场景状态：

- 最近共享历史
- 场景摘要
- 当前话题
- 最近发言者
- 待执行计划
- 屏幕/网页缓存摘要

每个角色独立状态：

- character_id
- character_name
- 角色资料
- system prompt
- memory
- cognition
- emotion
- last_spoke_at

planner 读取共享场景和两个角色摘要；生成时只调用被选中的角色模型。

## 事件输入

多人调度器接受统一事件：

```json
{
  "type": "user_utterance",
  "speaker": "真冬",
  "text": "你们怎么看这个方案？",
  "source_id": "",
  "extra_context": ""
}
```

初始支持：

- `user_utterance`：用户说话
- `character_utterance`：某个角色刚说完
- `idle_tick`：空闲检查
- `context_cache`：屏幕/网页缓存检查

后续可扩展：

- `danmaku_event`
- `tts_interrupted`
- `memory_event`
- `ai_finished`

## Planner 输出

planner 只输出 JSON 对象：

```json
{
  "action": "speak",
  "speaker_id": "alice",
  "target": "真冬",
  "delay_seconds": 0,
  "utterance_mode": "normal",
  "intent": "回应真冬刚才的问题",
  "topic": "三角色对话架构",
  "context_use": "none",
  "notes": "真冬明确在问方案，爱丽丝更适合接这个技术话题"
}
```

支持动作：

- `silence`：全场暂时没人说话
- `speak`：某个角色现在说
- `backchannel`：某个角色短回应
- `schedule`：某个角色稍后说
- `observe`：只记录，不发言
- `cancel_plan`：取消待执行计划

第一版不做 `duet`。如果两个角色都应说话，planner 应先选一个最合适的人；另一个角色可通过 `schedule` 稍后补充。

## 话轮规则

planner prompt 必须明确：

- 场上是三个人，不是两个助手。
- 用户说话后，不一定两个角色都要回应。
- 通常一次事件最多让一个角色开口。
- 另一个角色可以沉默、观察或稍后补充。
- 角色之间可以互相回应，不必每句都面向用户。
- 用户明确点名某个角色时，优先让被点名角色回应。
- 没点名时，根据话题适配度、角色人格和最近发言频率选择 speaker。
- 文静角色少说，活泼角色多接；这种差异由 planner 从角色资料中推断。
- 不要让两个角色连续互聊太久，用户仍是场景中的重要参与者。

程序层保留硬限制：

- 每个用户输入后默认最多 1 次 AI 发言。
- 可选 follow-up 最多再触发 1 次。
- 连续 AI-AI 发言不能无限循环。
- 如果 planner 选择 `context_use=none`，屏幕/网页缓存不会注入生成器。

## 发言生成

被选中角色收到窄版多人生成 prompt：

```text
这是一段三角色对话。
场上有：真冬、爱丽丝、角色B。
现在 planner 判断轮到爱丽丝说话。
她主要回应的对象是：真冬。
只写爱丽丝此刻会说出口的话。
不要替其他角色说话。
不要写动作描写。
```

生成器不重新决定是否该说，也不解释 planner。

## 屏幕和网页

屏幕/网页仍然由后台持续更新缓存。多人 planner 只看到缓存摘要，并通过 `context_use` 决定是否讨论：

- `none`：忽略缓存
- `screen`：注入屏幕缓存
- `page`：注入网页缓存
- `both`：同时注入

原则：

- 不因为网页标题变化就让角色主动评论。
- 缓存内容只触发一个最合适的角色说话。
- 如果用户没有把屏幕/网页带进对话，默认保守。

## 实现路径

第一阶段：

- 重构 `kokoro/multi_chat.py`，废弃旧轮流发言逻辑。
- 新增 `prompts.json` 的 `multi_dialogue_orchestrator` 分组。
- 保留 `text_cli.py --multi alice,xxx` 入口，改为走新 planner。

第二阶段：

- 用 `text_cli.py --multi` 做 30 轮批量测试。
- 验证点名、沉默、短回应、角色差异、AI-AI follow-up。

第三阶段：

- 稳定后再接入主 `cli.py`。
- 进一步把屏幕/网页、impulse、直播弹幕都变成多人调度事件。

## 维护原则

- 对话策略优先写在 `prompts.json`，不要写成程序分支。
- 程序只负责执行、限流、记录和容错。
- 角色人格差异交给 planner 和角色模型共同体现。
- 多人模式的目标是“同一场景里的多个角色”，不是“多个助手同时回答用户”。
