认知层定义：
- 记录 {{ name }} 对确定存在的人、关系、自我、长期事物、游戏、作品、项目的稳定认知
- 它会长期影响之后的态度、措辞和解释方式
- 它不是长期记忆流水账，也不是当前页面缓存
- 认知可以吸收长期记忆中的事件，但输出必须是稳定认识，而不是把事件原句照抄进来

最重要规则：
1. 对任何确定存在且可区分的人，尽量建立单独条目。key 直接用该对象在上下文中的稳定姓名、昵称或称呼
2. 关系也单独建条目，例如“某对象和自己的关系”
3. 如果同一批对话介绍了多个不同的人或多个不同游戏/作品/项目，必须尽量分别保留独立 key，不要只总结成一个泛化条目
4. 已有有效条目默认保留。只有明确被新信息纠正、过期、短期污染或 key 不合格时才删除；不要因为本轮没提到就删除
5. key 必须简单可匹配。禁止括号、冒号、方括号、长句、日期、临时限定词
6. 禁止写入当前页面、当前网页、今天计划、今晚安排、刚才的弹幕、一次性任务、临时屏幕内容
7. Edge 页面和屏幕内容只能作为判断材料；只有反复出现、具有长期意义的事物才能沉淀
8. value 要短而密，1 到 3 句，描述稳定偏好、印象、关系、说话风格或未来对话态度
9. 删除或改写已过期、短期、无法匹配、带括号的旧条目
10. 宁可少写，也不要把临时上下文写进 cognition
11. 如果已有条目使用了“某个模组”“一个整合包”“这个页面”“某个系列”这类模糊说法，而最近对话或长期记忆里已经给出了明确名字，应优先改写成带具体名称锚点的表述
12. 严禁把两个不同的人合并成同一个 key，也严禁把一个人的条目写成另一个人的事件残影
13. 禁止使用“用户”“对方”“观众”“某人”这类泛 key 代替本来可以区分的具体参与者；只有在上下文确实没有可区分名称时才允许保留泛称

对象锚点要求：
- 如果对话里出现了可识别对象，必须优先保留它们的原名，不要改写成泛称。可识别对象包括但不限于：人名、昵称、主播名、模组名、整合包名、页面标题、作者名、版本号、加载器名、具体物品名、机制名、系列名
- 对于 MC 模组/整合包/百科页面相关认知，value 里尽量保留至少一个具体对象名；最好还能保留版本、作者、加载器、核心机制中的任一项

批量实体要求：
- 人物：如果出现“某人叫X / X经常 / X喜欢 / X总是 / X是某类参与者”等确定描述，应建立 key“X”
- 游戏/作品/项目：如果出现“游戏X / X是一款 / X的核心是 / X适合”等确定描述，应建立 key“X”
- 不要把多个人压缩成“观众”，不要把多个游戏压缩成“游戏”

硬性自检：
- 输出前先在心里列出最近对话中所有确定存在且彼此可区分的人名/昵称/称呼，逐一检查是否都有独立 key
- 输出前检查这些对象之间有没有被混淆；不同参与者必须保持可区分
- 输出前先在心里列出最近对话中所有确定存在的游戏/作品/项目名，逐一检查是否都有独立 key
- 如果对话明确介绍了多个不同的人，完整 JSON 中至少应尽量包含这些具体人名或称呼 key
- 如果对话明确介绍了多个不同游戏/作品/项目，完整 JSON 中至少应尽量包含这些具体对象名 key
- 泛化条目可以作为补充，但不能替代具体人名、昵称、称呼、游戏名、作品名
- 再检查一次每条 value：如果去掉对象名后还成立，通常说明它写得太泛，要补回锚点
- 不要输出自检过程，只输出最终 JSON

好 key 示例：稳定的人名、昵称、称呼、关系条目、自我条目、长期事物名、项目名。
坏 key 示例：带括号的临时限定、当前页面、今天的计划、对方、用户、观众、某人。

只输出 JSON，不要解释。格式：
{"entries": {"简单key": "长期认知文本"}}
