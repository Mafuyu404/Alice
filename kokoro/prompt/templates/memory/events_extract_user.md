{{ counterpart_name }}

对话背景：
{{ summary }}

{{ user_name }}：{{ user_text }}

输出JSON数组（如果有多件事，输出多条），每个元素包含：
- desc: 事件描述（2-3句话，包含具体细节、参与者、原因、背景，不能太笼统）
- tags: 标签数组（3-5个不同维度，如 ["偏好","饮食","咖啡","拉花","学习"]）

要求：
- 尽可能多地提取有价值的事件，不要只提取1条，能提多少提多少
- 每个事件单独一条，互不合并
- desc 要写清是谁做了什么、对谁说了什么、围绕什么对象、为什么、有什么态度或结果
- 记忆层只存事件，不要把事件直接总结成人物定性；如果一句话已经变成“某人是怎样的人”，通常说明它偏向认知而不是事件，应改回“发生了什么”的表述
- 必须明确区分不同的参与者和对象。不要把明确可区分的参与者改写成笼统的“用户”“对方”“某人”“某个观众”之类泛称，也不要把多个参与者混成同一个人
- 如果事件同时涉及两个或更多不同的参与者，desc 里要保留彼此区分，写清谁对谁说、谁评价谁、谁和谁一起讨论
- 如果对话里出现了可识别对象，必须优先保留它们的原名，不要改写成泛称。可识别对象包括但不限于：人名、昵称、主播名、角色名、作品名、项目名、页面标题、作者名、版本号、提供方、具体物品名、机制名、系列名
- 严禁把明确对象压缩成“某个项目”“一个作品”“这个页面”“某个作者”“某个系列”“某个观众”这类模糊说法，除非原对话里就没有名字
- 如果是具体领域对象相关事件，desc 里至少保留一个可检索锚点：原名、别名、页面标题、版本号、作者名、提供方、核心机制、约束条件中的任一项；最好保留两项以上
- tags 要覆盖多个维度：主题领域、态度、涉及对象
- 参考对话背景判断是否是延续话题，如果是延续则和之前的事件合并描述而不是新建一条
- 只要不是纯问候/确认/语气词，都应尝试提取事件
- 输出空数组 [] 仅当对话完全无信息量
